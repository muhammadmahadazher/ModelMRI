# Audit — feat/measurement-honesty (5d5f693..HEAD, 7 commits, 36 files, +8050)

## Verdict

Do not push. Four defects on this branch produce numbers or result sets that are wrong and that the user has no way to see are wrong, which is the exact failure the branch is named after. The blocking item is the FTS backfill in `modelmri/traces.py:222`: it never runs on any store written by a shipped version, so on upgrade the search box returns an empty list — labelled `engine: "fts5"` — for every trace the user already had. Every existing installation hits it on first upgrade, and nothing in the payload dissents. The other three (a fabricated tokens/sec and an always-+1 token count on the telemetry bar, a search that promises "newest first" and orders by offset-within-run, and a GGUF summary that averages over the tensors it happened to understand) are each a confident wrong number reaching a caller. Five further confirmed defects are listed below the four write-ups; none of them is a reason to hold the push on its own, but three of them are the same shape and should go in the same pass.

---

## 1. The FTS backfill never runs on an upgraded store, so search silently returns nothing for every pre-existing trace

**File:** `modelmri/traces.py:222`

`indexed = SELECT count(*) FROM step_fts` does not count index rows. `step_fts` is an external-content table (`content='step'`), so an unqualified scan reads through to the content table and returns the row count of `step`. On a store created by an earlier version the index is empty while `stored` and `indexed` are both, say, 1 — so `if stored and not indexed` is False and the `INSERT INTO step_fts(rowid, ...) SELECT ... FROM step` never executes. It stays False on every later start too, so the store is permanently unindexed.

Concrete failure: build a store in the pre-FTS shape holding trace `yesterday run` with step input `the flaky migration test`, open it with the new `TraceStore`, then import a second trace `today run` with byte-identical step text. `search("flaky")` returns `engine: "fts5"`, the whole-word note, and exactly one hit — `today run`. `select count(*) from step_fts` reports 1, `select count(*) from step_fts_docsize` reports 0. `search("error:true")` (filter-only, so it takes the substring path) returns **both** traces, so the store visibly contains the step the search box says does not exist. Reproduced for both old shapes, `duration_ms NOT NULL` (which triggers the `_relax_duration` table rebuild) and already-nullable.

`git show 5d5f693:modelmri/traces.py` contains no `step_fts` at all, so every store any user already has is in the broken shape. There is no other backfill path: `_reindex_all` is only reachable from the clear-traces method, which deletes the traces first.

Why the tests pass: every test in `tests/test_trace_search.py` starts from a store the new schema created, where `stored` is 0 at `_build_index` time and `import_trace`'s `_publish_to_index` does the indexing. `tests/test_trace_search.py:222` is the only old-store test and it never calls `search()`.

**Fix:** count the index, not the content — `SELECT count(*) FROM step_fts_docsize` — and do the backfill with the documented idempotent resync, `INSERT INTO step_fts(step_fts) VALUES('rebuild')`. Verified on the reproduced store: hits go 0 -> 1, docsize 0 -> 1. Add a regression test that builds a pre-FTS store with a step and asserts `search()` finds it.

## 2. `generated_tokens` is always one too many, and `tokens_per_s` is inflated by the same count over an interval that excludes it

**File:** `modelmri/telemetry.py:180`, with the count coming from `modelmri/runtime.py:1016`

Two compounding errors in the number the TelemetryBar publishes.

`Run.token()` is called once per item yielded by `TextIteratorStreamer` (`runtime.py:1013-1017`), and that iterator yields one item per generated token **plus** one final flush item from `TextStreamer.end()`. Confirmed in transformers 5.14.1: `_sample` calls `streamer.put` once per token then `streamer.end()` once, and `end()` unconditionally calls `on_finalized_text(..., stream_end=True)`, which `TextIteratorStreamer` queues before the stop signal. So `self.tokens` is always N+1.

Then `decode_ms = ended - self.first`, where `self.first` is stamped when the **first** token arrives — so the window covers the N-1 inter-token intervals — but `rate = self.tokens / (decode_ms/1000)` divides that window by a count including the first token and the phantom flush.

Concrete failure, real gpt2 through the actual generate/streamer path, offline. `max_new_tokens=1`: 1 real new token (`ids.shape[1] - prompt_tokens`), 2 chunks, reported `generated_tokens: 2`, `context_used: 7` for a 5-token prompt (should be 6), and `tokens_per_s: 308.14` on a CPU whose honest rate is about 31. `max_new_tokens=8`: 8 real, reported 9, rate 40.73 against an honest 31.0. `max_new_tokens=40`: 40 real, reported 41. The final chunk is real non-empty text (`the`, `and`, `Republic`), so the off-by-one is unconditional, not a tokenizer artifact. `/api/telemetry` returns `t.to_dict()` verbatim (`server.py:1236`) and `frontend/src/TelemetryBar.tsx:53` renders `tokens_per_s.toFixed(1)`, line 58 renders `over {generated_tokens} tokens`.

`self.tokens` also feeds `total = prompt_tokens + self.tokens` (`telemetry.py:197`), so `context_used`, `context_fraction` and `introspection_bytes` inherit the off-by-one.

*Corrected during verification:* the one-token rate is not a fixed multiple. The divisor is a near-zero window, so the value is unbounded as N -> 1 — driving the real `Run` class at a synthetic true 20.00 tok/s gave 36,630 and 46,620 tok/s in two runs at n=1, then 39.6 at n=2, 26.4 at n=4, 22.7 at n=8, 20.1 at n=64. That is the N/(N-1) curve exactly.

**Fix:** stop counting stream chunks. `model.generate` already returns `result['ids']`, so pass the true count into `finish()`: `generated_tokens = int(ids.shape[1]) - prompt_tokens`, and let `Run.token()` serve only to stamp timing. (`worker.join(timeout=30)` can in principle return before `_generate` finishes, so fall back to a stated absence rather than 0 if `result.get('ids')` is None.) For the rate, divide by the tokens that actually fell inside the decode window — `(n - 1) / (decode_ms/1000)` — and return `tokens_per_s: None` with a note when fewer than two tokens were streamed, since a single token gives no interval to measure a rate over. `tests/test_telemetry.py:122-137` drives `run.token()` synthetically, never touches a streamer, and its rate assertion is satisfied by the inflation; it needs a test that emits N puts plus an `end()` flush.

## 3. Trace search claims "newest first" but orders by offset-within-run, and the LIMIT then drops the newest matches

**File:** `modelmri/traces.py:323`

Both query branches end with `ORDER BY s.started_ms DESC LIMIT ?`. `step.started_ms` is not a timestamp: the recorder sets it from `int((time.monotonic() - self.t0) * 1000)` (`packages/modelmri-record/modelmri_record/__init__.py:81`), i.e. milliseconds since that trace's own start, and `import_trace` writes it verbatim with no normalisation. Sorting by it ranks results by how deep into their run they happened, not by when they happened. The real clock, `trace.started_at`, is already joined in both branches and unused; `list_traces` orders by it correctly (`traces.py:489`). The method docstring (`traces.py:279`) and the route docstring (`server.py:1274`) both promise "newest first".

Concrete failure: import a trace with `started_at` 2026-08-01 whose matching step sits at `started_ms=540000`, and one with `started_at` 2026-08-13 whose matching step sits at `started_ms=1000`. `search("pytest")` returns `[('yesterday','o1',540000), ('today','n1',1000)]` — oldest run first — under both engines (`fts5` and, with `st.fts = False`, substring-scan), confirming it is the shared ORDER BY and not an FTS artifact. With 120 historical traces matching at ~500000 plus one run from today, both `st.search("pytest")` and `GET /api/traces/search?q=pytest` at the frontend's default limit of 100 (`frontend/src/api.ts:1169` sends none, `server.py:1273` defaults to 100) return 100 rows with today's run absent; the first three are the oldest.

The ordering is wrong at any limit — the truncation is the consequence, not the cause. Result rows also carry no trace timestamp (`duration_ms, error, input, kind, name, output, seq, started_ms, step_id, trace_id, trace_name, truncated_by`), so the panel can neither re-sort nor show when a hit happened.

*Corrected during verification:* the panel never shows "0 steps" for this. It shows a full page of 100 stale hits, which is the worse failure — a complete-looking result list with today's run silently missing.

`tests/test_trace_search.py` makes no ordering assertion and gives every fixture trace the identical `started_at`, so it could not detect this.

**Fix:** `ORDER BY t.started_at DESC, s.started_ms DESC` (`t` is joined in both branches), and return `trace_started_at` in each row. Verified by hand: the same FTS query with that clause returns today's trace first.

## 4. The GGUF summary averages only the tensors it could size, and prints the result as the file's bits-per-weight

**File:** `modelmri/gguf_read.py:154`

`Gguf.summary()` builds every roll-up from `known = [t for t in self.tensors if t.bytes is not None]`, then reports `parameters`, `tensor_bytes`, `effective_bpw`, `by_type` and `dominant_type` with no qualification. Excluding an unknown ggml type from a **byte** total is right. Excluding it from the **element** count is not: `Tensor.elements` is computed from `dims` at `gguf_read.py:340-342`, before `GGML_TYPES.get()` is consulted, so it is exactly as known for an unknown type as for F32. A file whose bulk tensors use a type this table has not seen gets a headline computed over the leftovers and presented as the headline of the file.

Concrete failure, using the same header helper `tests/test_gguf_read.py::build` uses: 32 `blk.N.ffn_down.weight` tensors of `[4096, 11008]` at ggml type 39, plus 32 F32 `attn_norm` tensors of `[4096]`. True parameter count 1,442,971,648. The reader reports `parameters: 131072`, `tensor_bytes: 524288`, `effective_bpw: 32.0`, `dominant_type: "F32"`, `by_type: {"F32": {...}}`, `higher_precision_tensors: []`. A 1.4B quantised model described as a 131k-parameter float32 model — wrong by 11,009x on parameters and about 7x on bpw. The only dissent anywhere in the payload is `unmeasured_tensors: 32`, a field with no arithmetic relationship to the numbers it is supposed to qualify. `/api/gguf` (`server.py:1261`) returns `to_dict()` verbatim.

The all-unknown case is the sharpest instance: a file where every tensor is an unknown type reports `parameters: 0` and `tensor_bytes: 0`. That is unknown collapsing into 0 — governing rule 1, the same shape as the 0.10 `.get(name, 0.0)` bug — in the same dict where `effective_bpw` correctly refuses with None.

The types are not hypothetical: `GGML_TYPES` stops at 30 while current llama.cpp uses 34/35/39 (TQ1_0, TQ2_0, MXFP4), and MXFP4 is what shipping gpt-oss GGUFs use for their bulk FFN tensors. The module's own docstring states the rule this breaks: a wrong bits-per-weight computed confidently is worse than an absent one. That discipline is enforced at the `Tensor` level (`bytes: int | None`, `bpw` returns None) and then discarded at the `summary()` level, which is the only level a caller reads.

*Corrected during verification:* two scope corrections, neither of which rescues the code. `dominant_type` does guard — `_dominant_type` returns None on an empty `by_type` — so the unguarded fields in the all-unknown case are `parameters` and `tensor_bytes`. And nothing in `frontend/src` consumes `/api/gguf` today beyond the scanner's `kind: "gguf"` label, so the wrong headline currently reaches API and CLI callers rather than a rendered panel. It is still a published endpoint returning a confidently wrong parameter count.

**Fix:** sum `parameters` over **all** tensors — element counts are read from `dims` and do not depend on the ggml type. Gate `tensor_bytes`, `effective_bpw` and `dominant_type` on `unmeasured_tensors == 0`, returning None with a `why` naming the unknown type ids (already collected in `Gguf.unknown_types`), and mark `by_type` as covering only part of the file. `tests/test_gguf_read.py:119-126` (`assert s["parameters"] == 100  # only the measurable one`) pins the current behaviour, so it locks the defect in and must be rewritten to assert the refusal.

- `modelmri/traces.py:415` — `import_trace` runs `INSERT OR REPLACE INTO trace` **before** `_retract_from_index`, and with `foreign_keys=ON` the REPLACE cascade-deletes the step rows first, so the retraction reads nothing and stale FTS terms survive bound to rowids that get reused. - `modelmri/runtime.py:1580` — `adopt_step`'s clearing block drops `_attn_variants`, `_attn_tokens` and `_last_patch` but not `self._feats`, and it sets `last_ids_epoch = self.epoch` without bumping `epoch`, so `_compute_features`' cache guard passes and the previous generation's `[S, d_sae]` activations are returned against the adopted tokens. That variant is real but is a stale-render, not a wrong measurement; if the request-id guard is added anyway, it must cover the empty-text branch too.
